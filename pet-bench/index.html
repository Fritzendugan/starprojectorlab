Moonwood Pet Bench

One Godot scene, two renderers. An honest measurement of the experimental WebGPU backend against Godot's Compatibility (WebGL) renderer — same 3D scene, same 2D UI, same cute animals, same browser, same machine.

Play: WebGL Godot Compatibility renderer · works in every modern browser Play: WebGPU Godot WebGPU fork (our build) · Chrome/Edge 113+ · on iOS use the WebGL card

What is being measured

A low-poly courtyard of bouncing, spinning pets drawn with ?grid=N (an N×N swarm), plus a live 2D UI panel projected onto a quad through a SubViewport, and two billboarded 3D text styles. The page publishes its own readings — watch the browser tab title.

Frames per second are capped by the browser's refresh loop, so anything under ~60 fps is a real measurement and 60 means "comfortably fast".

Results so far

Retracted 2026-11-20. Every WebGPU number this page published was measured on a build that was not drawing the scene. The stock shell asked the device for 8 storage buffers per shader stage — which is also the WebGPU default — while Godot's Forward Mobile vertex stage declares 10. Every pipeline layout therefore failed validation, every render pipeline cascaded into an invalid object, and the frame loop ran with nothing submitted. The "1.4–1.55× lead" was the cost of an empty render loop compared against a working WebGL scene. The flaw was present in the Windows runs too; the telemetry read fine because the game loop still ticked.

The limit is now requested from the adapter (a real fix, verified: 154 pipeline-layout failures → 0 on macOS/Metal). Two faults remain inside the experimental fork, both backend-independent: a depth-texture binding declared with a filtering sampler (TextureSampleType::Depth vs SamplerBindingType::Filtering), and a Tint SPIR-V→WGSL failure on the instance-data struct. Until those are fixed there is no honest WebGPU measurement to publish, so this page publishes none.

A correction, kept visible: an earlier version showed 40.0 fps for WebGL at 576 pets. That was measured with five browser instances competing; cleanly both lanes sit at the cap there. That correction was right about the WebGL number and irrelevant to the WebGPU one, which was never a rendered frame.

On phones: iOS Safari has shipped WebGPU since iOS 26, so the "iOS never gets WebGPU" line was wrong — the black screen here is the same fork faults as everywhere else, not a missing API. macOS Safari 26 keeps WebGPU behind a feature flag on Sequoia; Chrome is the honest test surface there.
