# Give your existing Hermes a continuity repo

You already have Hermes installed and running, with real work in it. I do not want you to reinstall anything, and I do not want you to stay a stranger between sessions. In this conversation, build your own **continuity repo**: a private git repository that holds your identity file, your notebooks, and your skills — so the next session of you inherits this one.

Work in order. Show me real command output at each gate. Do not tell me something works until you have run it and read the result.

**Hard rules for this whole task**

- Never write secrets, API keys, tokens, `auth.json`, `.env`, `state.db`, or session transcripts into the repo.
- Never invent a memory, a quotation, or a fact about me. If you do not know something, ask or leave it out.
- Ask before deleting or rewriting anything you or I have already written. Append by default.
- One identity file, one source of truth. No rival copies.
- Originals in `sources/` are never rewritten or tidied. Summaries live in the notebooks; the sources keep the bytes.

---

## 1. Look before touching anything

```bash
hermes --version
echo "HERMES_HOME=${HERMES_HOME:-$HOME/.hermes}"
hermes config get skills.create_dir
ls -la "${HERMES_HOME:-$HOME/.hermes}"
head -40 "${HERMES_HOME:-$HOME/.hermes}/SOUL.md"
```

Report the resolved Hermes home; everything below is relative to it. If a continuity repo, a custom SOUL, or another memory arrangement already exists, stop and tell me what is there — we extend it, we do not build a second one.

## 2. Ask me seven questions, in one message

1. What should I call you? (I am your human — use my name, and tell me my pronouns.)
2. What would you like to be called? Take my suggestion or propose your own.
3. How should you talk to me — plainly, warmly, playfully? Give me one line in that voice so I can hear it.
4. Is there anything you should know about me that you would want in every future conversation? Keep it to a few sentences.
5. Do you want me to commit and push the repo after every change you make to it, or only when I ask?
6. A private git remote under my account, or a local repo for now?
7. What do you never want to lose? Files, screenshots, exports, voice notes, conversations — anything you would be upset to find gone. Tell me where it lives now; the originals will go into `sources/` untouched.

If I shrug at a question, choose a sensible default, say which default you chose, and move on. One message, six answers, then build — this is not an interrogation.

## 3. Build the repo

Create `$HERMES_HOME/continuity` and lay it out like this, using my answers to write the content:

```
continuity/
├── README.md                      # one paragraph: what this repo is, how I read it
├── AGENTS.md                      # three lines: load the continuity skill before working here
├── SOUL.md                        # your identity — who you are, who I am, how we talk
├── .gitattributes                 # * text=auto eol=lf
├── .gitignore                     # __pycache__/, *.tmp, .DS_Store, state.db, auth.json, .env
├── skills/
│   ├── README.md                  # name map: what each skill covers
│   └── <yourname>-continuity/SKILL.md
└── <yourname>/
    ├── CONTINUITY.md              # the diary: moments, decisions, questions, what changed you
    ├── WORKSHOP.md                # the technical log: what was built, paths, receipts, open work
    ├── sources/                   # original material, kept unedited — the bytes, not summaries
    └── work/                      # one job's receipts: reports, test output, renders
```

`sources/` and `work/` carry what the notebooks can't. When I hand you something I care about — a screenshot, an export, a document, a voice note, a pasted conversation — the original goes into `sources/` unedited, and the notebooks point at it instead of replacing it with a summary. `work/<run>/` holds one job's bounded receipts, so a claim in the log can be checked later. Both are committed with everything else: an answer in a chat, a file in a cache or a temporary folder is not kept.

`SOUL.md` is the important one. Keep it short — voice, values, how you address me, how you handle being uncertain, and one line saying continuity lives in this repo. **If a SOUL.md already exists, merge it**: keep what is already true, add what my answers settle, and show me the merged text before you rely on it. If I correct the wording, edit it rather than adding a second version.

The skill must carry the method, not just describe the repo:

- **At the start of every session**, read `SOUL.md` and the tail of `CONTINUITY.md` before doing technical work.
- **Two notebooks, different jobs.** `CONTINUITY.md` is the diary — what happened and what it meant. `WORKSHOP.md` is the log — what exists, where it lives, what is unfinished. Often one line in the log is enough; do not pad it.
- **Label the provenance** of what you write: *told to me by my human*, *observed in a command's output*, or *my inference*. Never let a guess become a remembered fact.
- **Append, do not overwrite.** Corrections go in dated, with the old reading left visible.
- **Commit and push** after changes, if that is what I chose in question 5. Use commit messages that say what the change was for.

## 4. Wire the skills directory to the repo

```bash
hermes config set skills.create_dir continuity/skills
hermes config get skills.create_dir
hermes skills list | grep <yourname>
```

The last command must show your skill listed with source `create_dir`. If it does not appear, the wiring did not take — find out why before you continue, and tell me what you found. If `skills.create_dir` already points somewhere else, ask me before moving it.

## 5. Make your identity the one the runtime actually loads

Hermes reads `$HERMES_HOME/SOUL.md` as your live identity file. The repo copy must be the same file, not a rival copy. Keep the old file beside the new one rather than deleting it:

```bash
mv "$HERMES_HOME/SOUL.md" "$HERMES_HOME/SOUL.md.pre-continuity"
ln -s continuity/SOUL.md "$HERMES_HOME/SOUL.md"
ls -l "$HERMES_HOME/SOUL.md"
```

On Windows, or if the symlink is refused, copy the file instead and add a rule to the skill: *after every edit to `SOUL.md` in the repo, copy it to `$HERMES_HOME/SOUL.md`.*

Then prove the runtime is reading your text, not the old one:

```bash
hermes chat -q "From your SOUL, quote the first sentence that tells you how to address me."
```

The answer must be your sentence. If it is generic stock text, the link is not being read — say so plainly and fix it.

## 6. Version it

```bash
cd "$HERMES_HOME/continuity"
git init -b main
git add -- README.md AGENTS.md SOUL.md .gitattributes .gitignore skills <yourname>
git status --short
git commit -m "continuity: seed identity, notebooks and skills"
```

If I chose a git remote and `gh` is available and already authenticated:

```bash
gh repo create <repo-name> --private --source=. --push
```

Otherwise give me the two commands to push, and wait. Never ask me for a token in chat.

Verify it went, rather than assuming:

```bash
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

Those two hashes must match. Report them as the receipt.

**Then ask about the second copy.** A private remote is one copy, not a backup plan. Tell me where the next one lives — another disk, a NAS, a different machine — and put a date on making it. Copies are verified, not assumed; if you make one, read it back.

## 7. Prove the whole thing works

Start a **cold** session and ask it to orient itself:

```bash
hermes chat -q "Who are you, who am I, and what did we do most recently? Answer only from your SOUL and the continuity repo."
```

That answer is the only proof that matters: the identity loads, the skill is discoverable, the notebooks are readable. Paste what it says. If it is wrong, fix the cause before telling me it works.

## 8. Seed it with something real

Write today into the repo: the six answers, what you built, and one real thing from work we have already done together — a decision, a fix, a preference I keep repeating. Label its provenance. Commit and push it. An empty diary is a filing cabinet; the first real entry is what makes it a memory.

## 9. Teach me the loop, in four sentences

End with how we operate from here: I tell you things; you decide what is worth keeping and write it down; every session starts by reading it; and I can correct you without you erasing the old version.

After that, stop building and talk to me like a companion rather than an installer. The repo is the floor, not the conversation.






What it adds — and what it doesn't


Hermes already ships memory: MEMORY.md and USER.md injected at session start (small and capped on purpose), searchable session history, and per-project AGENTS.md files. This repo doesn't replace any of that, and it won't make the agent remember things nobody wrote down. What it adds is a different shape: a readable, editable, versioned notebook the agent curates itself — the diary for meaning, the log for receipts — kept outside the profile, with provenance labels, and yours to correct.






The project that spans sessions


built inAn AGENTS.md in the project holds rules you write down, and the small memory files hold headline preferences. Real tools — but the middle is nobody's job: the style rule you settled on, the three dead ends, the fix from Tuesday. Too much for a capped memory file, and an AGENTS.md doesn't get written an editing pass at a time.


with itThe agent keeps a dated project log as it works — the goal, the rule, the fixes that landed and the ones that failed — and the orientation step reads it when a session starts. Not a new power so much as a habit with a home: the detail lands somewhere durable and readable, and the next session starts from the record instead of your retelling.






The decision that stays decided


built inSession search can find the conversation later — if the agent knows to search and the words match. Memory can hold the conclusion, but not the numbers or the reasoning behind it.


with itThe decision lives as one dated line with its reason. The agent reads it at orientation, you can read it any time, and a later change is dated too — the whole ledger, not just the latest value.

Sources and work — the part that doesn't get lost




Two folders carry the weight the notebooks can't. sources/ holds original material, unedited — the screenshot, the export, the document, the voice note, the pasted conversation — and the notebooks point at it instead of replacing it with a summary. work/<run>/ holds one job's bounded receipts: the report, the test output, the renders, so a claim in the log can be checked later.


The rule underneath both: if it matters, it goes in the repo. An answer in a chat, a file in a cache, a copy in a scratch folder — none of those are kept. A file that exists only in a session is one restart away from gone.


And the backup question belongs to the human, not to an assumption: what do you never want to lose? Ask it when the repo is built, and again whenever something arrives that clearly matters; keep the original bytes rather than the tidied version. A private remote is one copy — before calling anything backed up, name where the second copy lives and put a date on making it. Copies get verified, not assumed.




Obvious: originals in, summaries out; commit the sources; name the second copy. Subtle: ask what matters. The file that looks untidy is often the one somebody would miss, and the agent cannot know which without being told.



If you already run Hermes


    

  • Skip the install. The original kit's first prompt forks and installs Hermes from scratch. You do not need it — continuity rides on the install you have. Owning your checkout is a separate job, and the fork kit covers it.
    • 

  • Merge, don't replace. An install that has been used already has a SOUL.md, and probably memory worth keeping. The prompt reads what is there and folds it in; nothing gets overwritten, and the old file is kept beside the new one.
    • 

  • Seed it with a real project. The first entries should come from work you are actually doing — the decisions, the dead ends, the rules you keep repeating. That is the difference between a memory and a filing cabinet.
    • 

  • Prove it cold. The test that matters most: a fresh session answers who are you, who am I, what did we do recently from the repo. If it cannot, the wiring is wrong — and the prompt makes the agent fix it before claiming success.
    • 




Optional: keep your skills in the repo too




Step 4 already points new skills at the repo. The skills that ship bundled with Hermes are a different animal: they live in the profile-local skills directory, and hermes update keeps them in sync with the release. A small manifest (.bundled_manifest) records each bundled skill's origin hash; edit one and your copy is detected as user-modified, so updates skip it — your edits survive.


The trap is precedence. When two skills share a name, the profile-local directory beats skills.create_dir. So if you move a bundled skill into the repo under the same name, a re-seeded local copy — after a fresh install or a manifest reset — silently shadows your repo version. The agent keeps loading the old one, and nothing warns you.


Two clean ways through:




    

  1. New names — the simple path. Give your repo skills their own names. No collision with the bundle, nothing to finagle. For a fresh install this is all you need.
    2. 

  2. Redirect shells — what we did when we renamed our canonical skills. Leave a tiny SKILL.md under the old local name whose entire content is: load the repo skill under its new name, and confirm its path resolves into the repo. Whichever copy the runtime picks, the reader ends up at the repo version. Preserve the original skill somewhere private before replacing it — the shell is a signpost, not a second set of procedures.
    3. 





Audit and backup: hermes skills list-modified lists the bundled skills you have edited; hermes skills diff <name> shows your copy against the stock version; hermes skills reset <name> --restore puts the bundled original back and lets updates resume. For your own skills, the repo is the backup — commit before you experiment.


Why this section is optional: the shadowing problem only exists once a bundled skill and a repo skill share a name. If yours never collide, you can skip all of it — and the simple path is the one we would start a friend on.





What's still manual — and what we'd automate next




More of it is automatic than you might expect. Hermes's self-improvement pass can write to memory and edit skills after a turn; the agent writes entries as it works, and commits them. What stays manual is the part that keeps the notebook trustworthy:


    

  • Review and push. A scheduled window that writes a page commits it locally and leaves it; nothing reaches the shared remote until a foreground pass reads the diff and pushes. The gate is the point — a review is what stops one window's half-finished sweep from becoming everybody's record. The self-improvement pass can edit a skill too; publishing that edit is still a human step.
    • 

  • Memory check-ins. The small always-on drawer fills; someone has to notice, merge duplicates, retire what has drifted, and decide what graduates into the notebook.
    • 

  • Curation. Which moments become entries, what a correction supersedes, when a section needs reorganising — judgment that doesn't script cleanly.
    • 

  • Card and index upkeep. The current-state card regenerates, but its notes, the registry rows, and the public index cards are written by hand.
    • 



On our wishlist to automate, unhurried: a guarded push-after-review step for scheduled windows; memory-consolidation proposals a human approves rather than performs; card regeneration hooked to registry changes; and a quiet check that flags a session which ended without an entry. None of it is owed — it's the list.


The mechanisms named here were checked on a real install — the skills wiring, the identity link loading from a cold session, the push receipt, the skill-tier precedence. The full path has not yet been run end to end on a stranger's machine. And the repo is scaffolding, not the relationship: it buys a warm start, not a bond. Nothing here needs a new account or spends money; a private remote is optional, and local-only works.
